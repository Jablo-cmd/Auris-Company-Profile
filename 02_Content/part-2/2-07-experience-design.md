# 2.7 Experience Design

**Layout:** Archetype H, the fixed ten-block service template.

---

## ① Service title

Experience Design
*Service covered: UI/UX design*

---

## ② Standfirst (40–55 words)

> A system can be functionally complete and still fail its users, if using it correctly requires
> knowledge the interface does not supply. We design for the person who has not been trained, not
> only the one who has.

---

## ③ Description

User interface and user experience design determine whether a technically correct system is actually
usable — whether a person can complete their task without external help, whether errors are
recoverable, and whether the interface communicates what the system is doing and why. This is
frequently underweighted in software procurement because it is not a functional requirement in the
conventional sense, and it is frequently the actual cause of a system's failure to be adopted.

We design interfaces around the task the user is trying to complete and the conditions under which
they complete it — attention available, prior training received, device in use — rather than around
the system's internal data model, which is the default a development-led build tends toward absent a
deliberate design discipline. Research, wireframing, prototyping and usability testing are scoped as
part of the design process, not skipped under schedule pressure.

---

## ④ Problems this solves

- A functionally complete system is under-adopted because users find it confusing or error-prone
- Support tickets are dominated by "how do I" questions the interface should answer without a call
- Different user groups (administrators, front-line staff, the public) are served by one
  undifferentiated interface built for none of them well
- A system's interface was designed around its database structure rather than the user's actual task

---

## ⑤ Business benefits

- Reduced training time and support burden, because the interface itself teaches correct use
- Higher adoption of systems that were built correctly but designed poorly
- Fewer costly late-stage interface reworks, because usability is tested before build, not after
- Interfaces differentiated appropriately for distinct user groups with different needs and contexts

---

## ⑥ Typical deliverables

- User research and task analysis
- Information architecture and user flows
- Wireframes and interactive prototypes
- Usability testing, with findings incorporated before build
- Visual design system, consistent with brand identity
- Accessibility review against WCAG standards
- Design specifications for development handover
- Post-launch usability review

---

## ⑦ Ideal client profile

An organisation whose system is functionally correct but under-adopted, in active development and
wanting usability designed in rather than retrofitted, or serving user groups with meaningfully
different needs from a single system.

---

## ⑧ Expected outcomes

- Reduced task-completion time and error rate for end users
- Lower support and training burden attributable to interface confusion
- Improved adoption of systems that were previously functionally complete but under-used
- Interfaces that meet recognised accessibility standards rather than excluding users by default

---

## ⑨ Technologies used

Design and prototyping tooling is methodology-led rather than platform-led; specific tools are
confirmed against `04_Technical Capabilities`, section 4.0, where relevant to a given engagement.

---

## ⑩ Industries served

Relevant across all ten sectors we serve, with particular weight where systems are used by the
public or by staff with limited technical training — government, healthcare, education and financial
services.
